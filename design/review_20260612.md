## A. 正しさ関連で残る作業

### A-1. ［修正済み・記録として保持］schur.pmop の multiset 誤用
multiset matcher は `::` の取り出しで x ≠ y を強制するため、Schur の主張が**偽**になっていた。
反例: red = {1,2,4}, blue = {3,5}。x ≠ y の Schur 組 (1,2,3), (1,3,4), (1,4,5), (2,3,5)
はいずれも単色でない。定理の成立には x = y の組 (1,1,2), (2,2,4) が必要で、
取り出しても target が減らない set matcher が正しい（pwl-schur.md の分析どおり）。
**「matcher の選択を誤ると主張が偽になる」実例として、論文のモチベーション節への
転用を推奨**（E-4）。

### A-2. Lean 比較コードのコンパイル検証（未実施）
- 各 pwl-*.md の Lean 4 側は `...` 穴や未確認の補題名
  （例: `Finset.exists_three_le_card`）を含むスケッチ。論文化前に必ず
  Lean 4 + Mathlib でビルド確認すること。
- Ramsey の `monochromatic` に相異性を追加する修正は適用済みだが
  （Mathlib の `Sym2` は対角元を含むため、相異性なしでは定理が自明に成立していた）、
  修正後のコードも未コンパイル。

### A-3. hall.pmop の neighbors_3 の dedup 要件（実装時に要徹底）
仕様コメントとして「N(S) は台集合（support）で数える」と明記済みだが、
`neighbors_3` / `size_3` は primitive のまま未実装。素朴な multiset 内包で実装すると
重複辺で Hall 条件が誤判定され hall_3 が偽になる
（反例: G = ⟦(0,0), (0,0), (1,0), (2,2)⟧）。

### A-4. Erdős–Szekeres の order-type reduction 補題（未形式化）
erdos_szekeres.pmop は値域を Fin 5 に取った有限版に修正済み（これで decide が正当化される）。
一般の ℤ / ℝ 列に対する主張へ戻すには、「互いに異なる 5 項の単調部分列の存在は
値の相対順序のみで決まる」という帰着補題が必要。未着手。

## B. 体系の中核に関わる未解決の設計課題

### B-1. `exhaustive by` 規則への制約導出の組み込み【最優先】
overview.md の型付け規則は各腕に変数束縛 `xᵢ : τᵢ` しか加えないが、
すべての証明例は「マッチ成立から導出される関係」（`c 2 = col'`、`col' ≠ col`、
相異性、`edge ⟦(v,x)⟧ = c` など）が文脈に入ることに依存している。
規則を `Γ, xᵢ : τᵢ, hᵢ : C(pᵢ, e, M) ⊢ bᵢ : U` の形に拡張し、
**matcher ごとに導出可能な制約スキーマ C を明示的に列挙する**ことが必要。
これが論文の技術的コアになるはず。最低限必要なスキーマ:

| パターン構成要素 | 導出される制約 |
|---|---|
| Sym2 のペアパターン `(p₁, p₂)` | 両端の相異（自己ループ非マッチ） |
| multiset の `::` | 出現の相異。対象が duplicate-free（関数グラフ等）のときに限り値の相異 |
| set の `::` | なし（target が減らない） |
| `#e` / `!#e` | 等式 / 不等式 |
| `p₁ & p₂` | 両制約の連言 |
| `p₁ \| p₂` | 選言（腕では分岐） |
| list の `_ ++ p :: _` | 位置の順序 i < j、区間長の下限 |
| `?(pred)` / `where` | 述語の成立 |

### B-2. パターン一致のアダプタ規則
`exhaustive by` の「補題パターンと match 腕の字面一致」が、実際の使用例では
次の暗黙の変換（アダプタ）を要している。verbatim 一致に限定するか、
健全なアダプタ集合を規則として定義するか、決める必要がある:

1. **キー射影 lifting**（pwl-schur.md の証明）: 色の値 `(c 3)` 上の補題
   `#col | #col'` で、関数 `c` 上の腕 `3 → #col :: _` / `3 → #col' :: _`
   の網羅性を正当化。「キー k での射影マッチ ⇔ 値マッチ」の同値規則が必要。
2. **ワイルドカードの capture 細分**（pwl-pumping.md の系 pumping_lemma）:
   補題の `_ ++ $q :: _ ++ #q :: _` に対し腕は `$pre ++ $q :: $mid ++ #q :: _`。
   `_` → `$x` はマッチ成否を変えないので健全だが、規則化が必要。
3. **腕の並べ替え・`_` 尾部の弱化**: 選言パターンの順序と腕の順序の対応、
   末尾 `_` の精粗。

### B-3. counting 層の不在【体系の最大の穴】
container + size 制約 + witness の三本柱のうち、size（数え上げ）側の体系が未設計:

- ramsey.pmop / pwl-ramsey.md の `pigeonhole_edges_at` の証明中の入れ子 match 群に
  `exhaustive by` が付けられない（その網羅性こそが数え上げ: deg(v) = 5、
  取り出すごとに残りが減る、2 色性）。現状 TODO コメントで保留。
- 旧 `pigeonhole_5_edges_2_colors` はどこにも定義がなかった（参照は削除済み）。
- pigeonhole.pmop の一般形は (i) 第 2 選言肢に**可変長パターン**（Fin n の全要素を
  1 度ずつ消費する形）が必要、(ii) フォールスルーの**負情報**（前の腕の失敗）を
  型文脈に取り込む規則が必要、(iii) `right (ih ...)` の持ち上げが不正確、の 3 点で未完成。

**提案**: matcher 代数のレベルで一般化された鳩の巣メタ定理を一度だけ証明する:

> duplicate-free な container matcher M、decidable な値域 B、
> |container| > |B| ならば `$x → $y :: $z → #y :: _` がマッチする。

各事例（Ramsey の 5 辺、Pumping の |Q|+1 状態、一般 pigeonhole）はこのインスタンス化で
閉じる。これが立てば「example の寄せ集め」を超えた技術的貢献になる（E-2 と接続）。

### B-4. `matches … ensuring Q` 拡張の要否
pwl-pumping は「核定理（matches 命題）+ 系（∀ k は exact 内で補題適用）」の
二段構成に修正済み。代替案として、マッチ成立時に派生値が満たす性質を主張構文に
取り込む `matches P as M ensuring Q` のような拡張も考えられる。
表現力は上がるが新機構が増える。当面は系方式で十分か、事例を増やして判断。

### B-5. フォールスルー方針の明文化
ramsey / schur は後続の腕に `!#` を明示する方針（負情報を構文に出す）、
pigeonhole.pmop は暗黙のフォールスルーに依存。前者を設計原則として明文化すべき。
ただし一般 n では B-3 (i) の可変長問題に帰着する。

## C. 表記・体系統一の設計判断（未決）

### C-1. `as` 節の引数規約と matcher の kinding
現状 3 通りが混在:
- 対象の型全体: `as multiset (Sym2 (Fin 6) → Color)`（ramsey, schur）
- 要素型: `as list Q`（pumping の pigeonhole_list）
- 関数の「グラフとしての観察」を含む overload（`multiset (A → B)` は
  実際には (A × B) ペアの多重集合の matcher）

`Matcher T` のような kind を導入し、`target : T`, `M : Matcher T`, `e matches P as M`
に統一するのが本命。prelude.pmop の `primitive matcher multiset : {A : Type} → A → Type`
というシグネチャの整形もこれに従属。型と matcher の区別は pwl-hall.md に
`BipartiteGraph X Y`（型）/ `bipartite_graph X Y`（matcher）として一例を入れた。

### C-2. ガード構文の統一
`where |X'| > |Y'|`（pwl-hall.md）と `?(predicate)`（prelude.pmop, erdos_szekeres.pmop）
の 2 系統。意味は同じ（束縛済み変数上の bool 述語、失敗で枝落ち）。どちらかに寄せる。

### C-3. bipartite_graph matcher のインタフェース統合
prelude.pmop 版（隣接関係 `A → B → Bool` ベース、matching 取り出し中心）と
pwl-hall.md 版（`⤳` による部分グラフ閉包、`matching_of` パターンコンストラクタ）が
別物のまま。名称は bipartite_graph に統一済みだが、インタフェースの統合と
`⤳` / `matching_of` の意味論・健全性の厳密化（pwl-hall.md §E）は未了。
`matching_of` を「matcher 変換子」（Matcher T → Matcher T）として一般化できるかも論点。

### C-4. theorem ヘッダ糖衣の target 選択規則
`theorem f (e : T) ... matches P as M` の糖衣で、複数パラメータがあるとき
（hall_3 の (G, hall) など）どれが matches の対象かの規則が未定義。
「matcher の対象型と一致する最後の非仮定パラメータ」等の規則を明文化するか、
pumping のように target を常に明示する形に統一するか。

### C-5. 記法の細部
- `M ⊢ w`（DFA の受理）: 判断の turnstile との衝突。定義節を設けるか記法変更。
- `⟦...⟧`: multiset リテラルと Mathlib の `Sym2` 構成子 `⟦(x,y)⟧` で意味が違う。
  論文では要注意。
- Sym2 の自己ループの扱い: 「型としては mk x x を許し、ペアパターンが
  対角元にマッチしない」という matcher 側責務に統一済み（prelude.pmop の選択）。
  標準の Sym2（対角元を含む）と異なるため、論文では名称・定義を明示すること。

## D. 関連研究（論文執筆時に追加すべき）

overview.md の関連研究リストに以下を追加し、特に最初の項目とは novelty の線引きを
明示的に書くこと:

- **Matching logic（Roșu; K framework）**: 「命題 = パターン」を掲げる体系。
  名前の衝突だけでも比較が必須。相違点: 本研究は MLTT 内の ∃ 命題としての
  matches + 非自由データ型 matcher + 非線形パターンによる witness 抽出。
- **Curry の functional patterns（Antoy & Hanus）**: `_ ++ x :: _` 型のパターンの先行。
  pwl-pumping の「古典的慣用句」の出典として引く。
- **Active patterns（Syme et al., F#）/ Scala extractors**: matcher による
  パターン語彙拡張の先行系譜（ただし statement 側ではなく term 側）。
- **AC マッチングの計算量（Maude / ELAN 系）**: multiset マッチングは
  AC マッチングであり一般に NP 困難。型検査コスト・decide の実現可能性の議論に必要。
- **Egison の matcher 適格性（既発表の matcher well-formedness 議論）**:
  「declarative / operational 意味論の一致」(overview.md) の証明義務をここに接続。
- **SAT による組合せ論の確定（Heule の Schur Number Five 等）**:
  `decide` を核言語プリミティブに置く設計の文脈付け。
- （既存リストの Cockx らの dependent pattern matching 文献は、B-1 の
  「マッチからの制約導出」の形式化の参考になる。）

## E. 論文戦略（レビューからの提言）

1. **比較軸を行数から statement 忠実度へ**。overview.md 自身が「核心的価値は
   証明の簡潔性ではない」と宣言しているのに、pwl-* の比較表は行数が主役で
   内的緊張がある。しかも有限インスタンスは Lean でも `by decide` 一行で閉じられる
   ため、行数比較は崩れやすい。強いのは「主張が informal な数学記述と同型」
   「補助述語ゼロ」「主張と適用の構文一致」の 3 点。
2. **一般パラメータ n の旗艦例を 1 つ完成させる**。現状の完成度の高い例は
   すべて固定有限インスタンスで、「全部 decide で閉じる世界で pattern style は
   何を買うのか」という査読の定番質問に弱い。B-3 の鳩の巣メタ定理 +
   一般 pigeonhole か pumping lemma が候補。
3. **matcher 追加の証明義務テンプレート（matcher 代数）を 1 節立てる**。
   Hall の `⤳` が「定理ごとの bespoke matcher」ではなく「方法」に見えるようにする。
4. **A-1 の Schur 反例を教材化する**。「multiset で書こうとして違和感がある定理は
   別の構造を使っている」という診断的主張（pwl-pumping §D）の最強の証拠。
5. 実装は現状スタブ（src/ 約 50 行）。主張を「設計 + 核言語の健全性 +
   ケーススタディ」に置くなら CPP / ITP 系、ビジョン重視なら Onward! /
   ‹Programming› 系が射程。いずれも B-1 が最初の関門。

# 現在の設計と実装前の確認事項（2026-10-08）

対象は `design/*.md`、`sample/pmop/*.pmop`、既存の Haskell 実装である。
この確認では、設計文書とサンプルの誤植・記述の不整合を修正した。
新しい言語機能の実装や、各サンプルの証明の完成は行っていない。

## 1. 設計の中心

定理の主張を `e matches P as M` と書き、パターン P によって
「e の中にどの構造が存在するか」を表す。M はそのパターンの解釈と対象の分解方法を
与えるマッチャーである。証明から構成要素を取り出すときも同じパターンを使い、
`exhaustive by lemma` で網羅性を与える。

基礎には依存関数型、帰納型、命題等式 `Id`（二つの値が等しいことの証拠の型）を置き、通常の `match` を
`matches` の証拠から値を取り出す操作として導く方針である。
中心例は Ramsey、Schur、pumping lemma、一般の Hall の結婚定理である。
この主張と例題は維持し、以下の不足を埋める。

## 2. 現在の実装

依存関数型（Π 型）は結果の型が入力値に依存する関数の型、Σ 型は値とその値に
依存する証拠を組にする型、宇宙は型を要素として持つ型である。

| 項目 | 実装で確認できるもの | 提案する言語に向けて必要なもの |
|---|---|---|
| 構文 | `.pegi` の `data`、`define`、関数、帰納型パターン | `.pmop` の宣言、`matches`、`exhaustive by`、マッチャー |
| 型と項 | Π 型、Σ 型、宇宙、帰納型を表す構文木 | 証明に用いる各構成の形成・導入・除去規則 |
| 検査・評価 | 関数や帰納型パターンの型検査、変換可能性の検査、評価 | 基礎体系の検査の補強と、新しい証明規則の実装 |
| 等式 | サンプルで帰納型として宣言する `Eq` | 設計案の組み込み `Id` とその除去規則 |
| 例題 | `sample/*.pegi` は既存構文の例 | `sample/pmop/*.pmop` は設計スケッチであり、現在のパーサでは処理できない |

構文木に Σ 型があることと、
利用者向け構文や検査の全経路が完成していることは区別する必要がある。
関連する実装は [AST.hs](../src/Language/EgisonProver/AST.hs)、
[Parser.hs](../src/Language/EgisonProver/Parser.hs)、
[Check.hs](../src/Language/EgisonProver/Check.hs) にある。

既存の試作をそのまま証明の最終検査器（カーネル）として使うことはできない。
少なくとも、次の箇所を補強する必要がある。

- `check _ UndefinedE _` は任意の期待型で未定義項を受理する。
  証明の完成を判定する際は未解決の穴を拒否する必要がある。
- `checkTopExpr` は `DataDecE` を検査せず返す。
  帰納型の宣言について、型の形成、コンストラクタの結果型、厳密正値性
  （定義する型がコンストラクタの引数の関数入力側に現れない条件）を検査する必要がある。
- 定義の型・本体があらかじめ全体の環境に登録され、再帰の停止検査がない。
  自己参照を許すだけでは証明にならないので、構造に従う再帰とその検査規則が必要である。
- `AST.substitute1` は名前による代入で、変数の捕獲を防ぐ処理がない。
  また Π 型・Σ 型では束縛名が代入対象と同じとき、束縛の外にある引数型への代入まで
  省略している。束縛の表現と代入を整理してから依存する証明規則を追加する必要がある。

## 3. 今回修正した不整合

- overview の鳩の巣補題と腕を、現在の Ramsey 例の `pigeonhole_edges_at edge v`
  と `(#v, $x)` に同期した。「ハイパシス」は「仮定」に直した。
- `triangle_two_color_exhaustive` に3頂点の相異性の前提を補った。
  `x = y = z` ではペアパターンが自己ループを拒否し、どちらの選択肢も成立しない。
  主定理では外側のマッチから得られる相異性の証拠を渡すため、主定理の主張は変わらない。
- Lean の pumping 例の語の反復を `(List.replicate k y).flatten` に直した。
  `List.replicate k y` だけでは語のリストになる
  （[Lean のリストの定義](https://lean-lang.org/doc/reference/latest/Basic-Types/Linked-Lists/)）。
- pumping の走行列は |Q|+1「ステップ」ではなく、初期状態を含む |Q|+1「個の状態」である。
  また中間リストは空でもよく、繰り返し状態の位置の差は `|mid| + 1` である。
- Hall の反例の隣接先、参照先の節番号、空集合を除く帰納法の条件を直した。
  `Multiset (Fin 3 × Fin 3)` は無限個の値を持つため、512通りの辺集合への帰着を
  証明してから全数検査する必要があることを明記した。
- Hall の `matching_of` は使用箇所では matcher の変換であり、パターンコンストラクタではない。
  `¬ (... ∧ ¬ ...)` の説明も「三重否定」から「入れ子の否定」に直した。
- prelude の Sym2 が対角元を含むこと、バリューパターンの実行条件と命題としての
  使用条件の区別、定理ヘッダでの target 省略の説明を修正した。
- 旧補題名、Schur 数の `S(2)` 表記、未定義の反対色関数などを同期した。
  旧レビューの「実装は約50行のスタブ」という記述を訂正した。

## 4. 最初に確定する設計

### 4.1. `matches` の証拠と除去規則

現状の存在量化による説明を、次の三つを指定する形に進めるのがよい。

1. 各パターンが束縛する値の型と、その依存関係。
2. 束縛した値と target の関係を示す証拠の型。
3. `match` の各腕が受け取る値と証拠、および返す結果の型。

例えば multiset の `::` は、選んだ値と残りだけでなく、元の多重集合が
それらで構成されるという証拠を必要とする。`#e` は命題等式の証拠を与える。
or パターン（複数のパターンのいずれかにマッチするパターン）の選択肢が異なる変数を
束縛する場合も、選択肢ごとの証拠として扱う必要がある。
`exact ⟨…⟩` の自動処理は、これらの証拠を構築してカーネルに検査させる形にする。
`pumping_lemma` の長さ・状態遷移なども、証明済みの補題から導出する。

`exhaustive by` は網羅性を与えるが、複数の成功するマッチや複数の腕があるときに
どれを選ぶかはまだ決まっていない。証明の証拠を使う除去と、実際に探索して値を選ぶ実行を
どのように対応させるか、評価規則も必要である。

### 4.2. マッチャーの型と分解後の対象型

`as multiset (A → B)`、`as list Q`、prelude の `A → Type` という宣言は、
まだ同じ規約になっていない。マッチャーの対象型と、子パターンが受け取る型を明示する。

特に Ramsey の `$edge'` / `$edge''` は辺を取り出した残りであり、
元の全関数 `Sym2 (Fin 6) → Color` ではない。
残りを有限な入出力ペアの多重集合として持つか、部分関数として持つかを決め、
子パターンと入れ子の `match` に渡すマッチャーの型を合わせる必要がある。
元の全関数をそのまま返すと、取り出した辺を再使用でき、相異性や数え上げが崩れる。

Hall の `G matches $f as matching_of …` にも同じ問題がある。
通常の `$x` は対象全体を束縛する一方、ここではグラフ G から関数 f を取り出す。
この変換による束縛の型と、f が完全マッチングである証拠の受け渡しを定義する。

### 4.3. 宇宙と基礎体系

overview の「Type（1宇宙）」と、既存実装の `UniverseE n` および
`Universe n : Universe (n+1)` は一致していない。
一つの小さい宇宙を使う方式と宇宙の階層を使う方式のどちらでも、宇宙自身の型と
Π 型・Σ 型の形成規則を明示する必要がある。単に `Type : Type` として閉じてはいけない
（[Lean の宇宙の説明](https://lean-lang.org/doc/reference/latest/The-Type-System/Universes/)）。
また `Id` の除去、再帰の停止性、帰納型の検査を揃える。
実行時の型の安全性だけでは、偽の命題を証明できないことまでは保証されない。

## 5. 続いて詰める設計と証明

- **数え上げ**：固定頂点からの同色3辺、一般の鳩の巣原理、list 上の重複状態を
  共通の数え上げ補題で扱う。`pigeon_step` の結論は衝突と別のパターンの選言なので、
  衝突だけの腕を正当化するには第2選択肢が不可能であることの証明も必要である。
- **パターン間の変換**：変数名の変更、ワイルドカードを変数として束縛する変更、
  キーでの射影、腕の順序変更を、証拠の変換として定義する。
  Schur の外側の1腕にも、全関数をキー1で観察できる網羅性の証明が必要である。
- **否定とガード**：`!p` で外に出せる束縛、`!#e` の不等式の証拠、
  `where` と `?(pred)` の関係を決める。命題としての不成立と探索の失敗は、
  探索の完全性を証明してから結び付ける。
- **算術のバリューパターン**：Schur の `PosFin n`（1,…,n の有限型）の和は範囲外になりうる。
  `Option`（値または値の不在を表す型）を返す `addBoundedPosFin` を通常の `#e` にどう組み込むかを決め、
  範囲内の値とその証拠を扱う規則を与える。
- **有限性と `decide`**：等式が判定できることと、すべての候補を有限個として
  列挙できることは別の条件である。有限関数を観察する matcher に必要な列挙の証拠、
  Hall の台集合への帰着、および判定結果から証明項を構成する規則を用意する。
- **一般の Hall**：`.pmop` の辺の取り出しと、設計文書の `⤳` / `matching_of` を
  同じ型・意味論に揃える。一般形の存在証明と matcher の正しさを完成させる。
- **数値の等号までの証明**：Ramsey の K₆ に対する存在証明に加え、K₅ の反例を
  証明する。Schur も {1,…,4} の反例と {1,…,5} の存在証明を揃える。
- **比較と評価**：Lean の例もビルドし、主張の表し方、必要な補助述語、証明からの
  値の取り出しを比較する。現在の行数表は未完成の証明スケッチの概算であり、
  実装後に同じ定理と検証済みのコードを使って測定する。

実装は 4.1–4.3 の規則を確定してから進める。最初の完了条件は、
単純な `matches` の証拠を構築・検査し、`exhaustive by` で取り出した値と
等式の証拠を次の証明で使えることである。その後、一般の鳩の巣原理を完成させ、
Ramsey と Schur、走行列と pumping lemma、一般の Hall へ進む。

## 6. 今回の検証

処理系から独立した有限列挙で、次を確認した。

- K₆ の全32,768通りの2色塗りで単色三角形と固定頂点の同色3辺が存在すること。
- 相異なる3頂点の網羅性補題の全色ケース、および相異性の前提を落とした反例。
- {1,…,5} の全32通りの2色塗りで Schur 三つ組が存在することと、x ≠ y に限定した反例。
- 3×3 の二部グラフの全512通りの辺集合で Hall 条件と完全マッチングの存在が一致すること、
  および隣接先の重複を数えた場合の反例。

文書のリンク、コード区切り、表の列数、`git diff --check` も確認した。
これらは数学的な有限ケースと文書の確認であり、未実装の `.pmop` 言語の型検査や
一般形の証明の代わりにはならない。Lean の例は穴を含むため、全体のビルドは未実施である。
Haskell の実装は変更していない。

Lean 側の列挙型宣言は `inductive Color where | red | blue` の形に統一した。
Lean 4.31.0 では `where` を省略した元の形も受理されるが、`:= red | blue` は
最初のコンストラクタの前の `|` がないため構文エラーになる。
`DecidableEq` を導出する単独の宣言で、元の形と `where` 付きの形が通ることを確認した。
Mathlib に依存する `Fintype` の導出を含むビルドは未実施である。

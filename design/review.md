# 設計と実装上の課題

`design/*.md` と [完全なコード](examples/README.md) に記す言語設計、および Haskell 実装の
現在の状況と、実装・証明を完成させるための課題をまとめる。
確認日：2026-10-09。

## 1. 設計の中心

定理の主張を `e matches P as M` と書き、パターン P によって
「e の中にどの構造が存在するか」を表す。M はそのパターンの解釈と対象の分解方法を
与えるマッチャーである。証明から構成要素を取り出すときも同じパターンを使い、
`exhaustive by lemma` で網羅性を与える。

パターンは等式変形や帰納法の途中でも使う。定理の結論が等式や要素数の性質でも、
関係を持つ要素と残りを取り出し、各分野の補題や帰納仮定へ証拠を渡せる。
適用範囲を考える際は、定理の分野と、証明中の選択・分解の役割の両方を扱う。

基礎には依存関数型、依存対型、宇宙の階層、帰納型、
命題等式 `Id`（二つの値が等しいことの証拠の型）を置き、通常の `match` を
`matches` の証拠から値を取り出す操作として導く方針である。
中心例は Ramsey、Schur、pumping lemma、一般の Hall の結婚定理である。
以下では、この設計の実装と証明に必要な作業を整理する。

## 2. 現在の実装

依存関数型（Π 型）は結果の型が入力値に依存する関数の型、Σ 型は値とその値に
依存する証拠を組にする型、宇宙は型を要素として持つ型である。

| 項目 | 実装で確認できるもの | 提案する言語に向けて必要なもの |
|---|---|---|
| 構文 | `.pegi` の `data`、`define`、関数、帰納型パターン | `.pmop` の宣言、`matches`、`exhaustive by`、マッチャー |
| 型と項 | Π 型、Σ 型、宇宙レベル、帰納型を表す構文木。Σ 型・対・射影には検査・評価の処理もある | Σ 型・対・射影のパーサと、各構成の形成・導入・除去規則の検査 |
| 検査・評価 | 関数や帰納型パターンの型検査、変換可能性の検査、評価 | 基礎体系の検査の補強と、新しい証明規則の実装 |
| 等式 | サンプルで帰納型として宣言する `Eq` | 設計案の組み込み `Id` とその除去規則 |
| 例題 | `sample/*.pegi` は既存構文の例。`design/examples/lean/` は比較用の完全な Lean プロジェクト | `design/examples/pmop/` は完全な提案ソース。現在のパーサでは処理できない |

構文木に Σ 型があることと、
利用者向け構文や検査の全経路が完成していることは区別する必要がある。
関連する実装は [AST.hs](../src/Language/EgisonProver/AST.hs)、
[Parser.hs](../src/Language/EgisonProver/Parser.hs)、
[Check.hs](../src/Language/EgisonProver/Check.hs) にある。

既存の試作をそのまま証明の最終検査器（カーネル）として使うことはできない。
少なくとも、次の箇所を補強する必要がある。

- `check _ UndefinedE _` は任意の期待型で未定義項を受理する。
  証明の完成を判定する際は未解決の穴を拒否する必要がある。
- `checkTopExpr (DefE n t e)` は本体を t に対して検査するが、t 自体が型であることを
  検査しない。`infer` の `TypeE` にも型引数・添字の検査がない。
  宣言を環境へ登録する前に、型の形成と引数・添字の型を検査する必要がある。
- `checkTopExpr` は `DataDecE` を検査せず返す。
  帰納型の宣言について、型の形成、コンストラクタの結果型、厳密正値性
  （定義する型がコンストラクタの引数の関数入力側に現れない条件）を検査する必要がある。
- 定義の型・本体があらかじめ全体の環境に登録され、再帰の停止検査がない。
  自己参照を許すだけでは証明にならないので、構造に従う再帰とその検査規則が必要である。
- `AST.substitute1` は名前による代入で、変数の捕獲を防ぐ処理がない。
  また Π 型・Σ 型では束縛名が代入対象と同じとき、束縛の外にある引数型への代入まで
  省略している。`Env.alphaConvertion` の名前変更にも束縛の範囲の扱いに不足がある。
  束縛の表現と代入を整理してから依存する証明規則を追加する必要がある。
- `checkCoverage` で使う `simplifyPattern` は `ValuePat` をワイルドカードに変える。
  バリューパターンの等式条件を網羅性の判定に残し、未検討の場合を受理しないようにする。
  `unify` には、変数自身を含む式への代入を拒否する検査がなく、
  固定された外側の変数と、解いてよいパターン変数の区別も必要である。
  型の変換可能性を調べる評価と等式の判定も、基礎体系の計算規則と揃える。

以上は現在のソースの確認に基づく。`.pmop` の規則の追加に先立ち、
完成した証明を受理・拒否する条件と、それを確認する検証を整備する。

## 3. 最初に確定する設計

### 3.1. `matches` の証拠と除去規則

`matches` を束縛値と関係の証拠の依存対として解釈し、次の三つを確定する。

1. 各パターンが束縛する値の型と、その依存関係。
2. 束縛した値と target の関係を示す証拠の型。
3. `match` の各腕が受け取る値と証拠、および返す結果の型。

例えば multiset の `::` は、選んだ値と残りだけでなく、元の多重集合が
それらで構成されるという証拠を必要とする。`#e` は命題等式の証拠を与える。
or パターン（複数のパターンのいずれかにマッチするパターン）の選択肢が異なる変数を
束縛する場合も、選択肢ごとの証拠として扱う必要がある。
`exact ⟨…⟩` の自動処理は、これらの証拠を構築してカーネルに検査させる形にする。
`pumping_lemma` の長さ・状態遷移なども、証明済みの補題から導出する。
[固定点のない対合](pwl-involution.md) では、重複のない対象の分解から
残りの台集合と要素数の関係を得て、元の写像の条件が残りでも成り立つことを証明する。
この証拠の受け渡しを、等式変形と帰納仮定の適用にも使えるようにする。

各パターン構成が与える関係を、マッチ成立の証拠から取り出す規則として定義する。

| パターン構成 | 腕で使える関係 |
|---|---|
| Sym2 のペアパターン `(p₁, p₂)` | 両端の相異性 |
| multiset の `::` | 選んだ要素と残りによる分解。対象に重複がない場合は選んだ値の相異性 |
| set の `::` | 要素の所属。取り出しても対象は減らず、値の相異性は要求しない |
| `#e` / `!#e` | 等式 / 不等式 |
| `p₁ & p₂` | 両方の関係 |
| `p₁ \| p₂` | 選択肢ごとの束縛と関係 |
| list の `_ ++ p :: _` | 分解位置、繰り返し使用時の位置の順序、区間長 |
| `?(pred)` / `where` | 束縛した値についての条件の成立 |

`match h : e as M` は腕の関係の証拠を h として受け取る。
証明の証拠を使う場合分けは、網羅性の証拠の選択肢を除去する。
複数の成功する腕がある場合も、各腕は自身の関係だけから結論を証明し、前の腕の失敗には依存しない。
探索による実行の順序と、得た結果が同じ関係を満たすことは実装時に検査する。

### 3.2. マッチャーの型と分解後の対象型

[コードの仕様](examples/README.md) で、マッチャーの対象型、子パターンの型、
残りの型、腕の関係の証拠を定める。
有限関数を多重集合として観察した残りは `Multiset (A × B)` とし、全関数として返さない。
Ramsey の内側の照合は元の `edge` を再び観察する。

Hall の `matching_of E` は、辺の関係 E に対して候補 f:X→Y とマッチングの証拠を返す。
通常の `$x` が対象自身を束縛する規則とは異なる専用の選択である。
全関数の有限列挙と、候補が満たす関係は完全なコードに定義する。
これらの数学的な型と関係を、パターンの型付けと核の証拠の型へ反映する。

### 3.3. 宇宙と基礎体系

核では宇宙レベルを区別する。既存実装は `UniverseE n` と
`Universe n : Universe (n+1)` を持ち、Π 型・Σ 型のレベルを引数型と結果型の
レベルから計算する。ただし、型の形成とレベル間の型の扱いの検査は完成していない。
利用者向けの `Type` の省略記法、帰納型と `matches` のレベル、
異なるレベルの型を同じ位置で使える条件も揃える。
単に `Type : Type` として閉じてはいけない
（[Lean の宇宙の説明](https://lean-lang.org/doc/reference/latest/The-Type-System/Universes/)）。
また `Id` の除去、再帰の停止性、帰納型の検査を揃える。
要素数や長さが減ることを証明して使う帰納法も、基礎体系から導出する。
実行時の型の安全性だけでは、偽の命題を証明できないことまでは保証されない。

### 3.4. 宣言の省略記法と束縛

完全なコードでは `theorem f (…) : e matches P as M` と書き、
対象 e とマッチャー M を明示する。パラメータから対象を暗黙に選ぶ規則は用いない。
`exact ⟨束縛値⟩ by proof` は、指定した値に対する関係の証拠を proof で構成する記法とする。

パターンの変数は、そのパターンが表す存在命題の内側で束縛される。
独立した命題にまたがって名前を参照する場合は、存在量化や証拠の取り出しを明示する。
否定パターンの中の束縛を外で使えるかどうかも、その規則に含める。

記法の意味は使用箇所で定義する。特に `M ⊢ w` は DFA による受理を表す記法、
`⟦…⟧` は多重集合の値または Sym2 の値を表す記法として、型と文脈を明示する。

## 4. 続いて詰める設計と実装

- **パターンの証拠の構成・除去**：[完全なコード](examples/README.md) の各関係を
  核の型に写し、`match h : …` で腕の値と証拠を束縛する。
  パターンの証拠を明示した Lean 版で検査した推論を、処理系の変換結果として再現する。
- **数え上げ**：一般の鳩の巣原理、固定頂点の同色3辺、走行列の重複を証明するコードは揃っている。
  その束縛値と関係を `matches` に構築し、同じパターンの腕で取り出す処理を実装する。
- **パターン間の変換**：変数名の変更、ワイルドカードの束縛、キーの観察、選択肢の並べ替えを、
  等式・選言・存在の証拠の導入と除去へ変換する。
  Schur のキー1の観察には `at_key` の証拠を用いる。
- **否定と条件**：`!p` の内側の束縛は、不成立を述べる命題の内部に限る。
  `!#e` は不等式、`?(P)` と `where P` は命題 P の証拠とする。
  群の語と歩道の負の腕で、この証拠を帰納法の停止ケースへ使う。
  命題の不成立と探索の失敗の対応は、探索の完全性とともに証明する。
- **算術のバリューパターン**：Schur の有限グラフではキーを自然数に写し、和も自然数に揃える。
  範囲外の和は所属しないことで除外する。型の一致と所属の証拠を処理系で検査する。
- **有限列挙と判定**：Hall の全部分集合の組と全関数の候補は、列挙と所属の意味を検査済みのコードに定義する。
  `decide` は判定の計算と証明項を結び付ける。等式の判定可能性と候補の有限性を別々に要求する。
- **pumping lemma**：`split_to_loop` の添字・長さ・状態遷移の完全な証明を、
  走行列のマッチの証拠へ接続する。任意の k の反復と受理保存まで処理系で検査する。
- **一般の Hall**：近傍の包含を表す `⤳` とマッチングを取り出す `matching_of` を、
  完全なコードの対象型と関係に揃える。
  一般の有限 Hall 定理の利用には、対応する定理の証明を核で検査するライブラリも必要である。
- **等式変形と帰納法**：対合の残りの閉性と減少、群の積の保存、置換の構成と合成、
  歩道の辺・始点・終点の保存を、全例の完全なコードから核の証明項へ変換する。
  要素数・長さに関する強い帰納法と、その小さい引数の証拠を検査する。
- **Erdős–Szekeres**：5項の場合は、相対順序への帰着と5項以上の列への拡張を含めて Lean で検査する。
  一般の r,s による長さ (r−1)(s−1)+1 の定理も、同じ順序を保つ選択と数え上げで形式化する。
- **比較と評価**：上界・下界を含む Ramsey と Schur、pumping lemma、一般の Hall、
  等式・帰納法の途中の例を完全なコードで比較する。
  定義・補助補題・主証明の範囲を揃え、証拠の受け渡しと適用範囲を評価する。

まず §2 の基礎検査を補強し、§3 の規則と上記の各関係を実装する。
最初の完了条件は、単純な `matches` の証拠を構築・検査し、
`exhaustive by` で取り出した値と等式の証拠を次の証明で使えることである。
その後、全例の完全な提案ソースを直接検査できるところまで拡張する。

## 5. マッチャーの検査・評価・関連研究

マッチャーを追加する際に必要な条件を共通の形式にまとめる。
パターンが表す関係と、実際の分解処理で得られる結果が一致すること、
各結果の値と証拠に型が付くこと、探索で必要な結果を取り出せることを証明する。
Hall の `⤳` / `matching_of` にもこの形式を適用する。

評価では、証明中の役割ごとの適用範囲、数学的な主張との対応、
利用者が書く補助述語の数、主張と適用のパターンの対応を中心に比較する。
一般の鳩の巣原理、pumping lemma、一般の Hall の
検証済みの証明を揃え、有限ケースの列挙と一般の証明の両方を示す。
定理の主張にパターンを使う例に加え、等式変形や帰納法の途中で使う例についても、
対象・分解後の型と各段階で引き継ぐ証拠を検査する。
Lean の比較コードと、パターンの証拠を明示した Lean コードは、
固定した Lean・Mathlib の下で一つのプロジェクトとしてビルドする。
Schur の set と multiset の意味の違いは、マッチャーの選択が主張をどう定めるかの
例として説明する。

関連研究では、次の比較と文献の確認を行う。

- **Matching logic**：命題とパターンを対応させる体系。本設計の存在命題、
  マッチャーによる分解、証明からの値の取り出しとの関係を明確にする。
- **Curry の functional patterns**：関数を使ってデータの分解を表すパターン。
  `_ ++ x :: _` によるリストの分解と非線形パターンとの関係を整理する。
- **F# の active patterns / Scala の extractors**：利用者がデータの分解方法を定義する機構。
  マッチャーによる語彙の拡張と、定理の主張にもパターンを使う設計を比較する。
- **結合律・交換律を持つ演算のマッチング**：多重集合の分解の計算量と、
  本言語で許すパターンの範囲における探索・型検査のコストを評価する。
- **Egison のマッチャーの検査条件**：型の検査と分解処理の正しさを保証する条件。
  本言語で要求するマッチャーの証拠との関係を整理する。
- **SAT による組合せ論の証明**：有限の論理式の充足可能性を判定する手法を用いた証明。
  Schur 数の研究などと、本言語の `decide` による証明の検査を比較する。
- **依存型を持つパターンマッチ**：マッチ成立時の型・等式の導出について、
  Equations や Agda の手法との関係を整理する。

## 6. 検証状況

処理系から独立した有限列挙で、次を確認した。

- K₆ の全32,768通りの2色塗りで単色三角形と固定頂点の同色3辺が存在すること。
- 相異なる3頂点の網羅性補題の全色ケース、および相異性の前提を落とした反例。
- {1,…,5} の全32通りの2色塗りで Schur 三つ組が存在することと、x ≠ y に限定した反例。
- 3×3 の二部グラフの全512通りの辺集合で Hall 条件と完全マッチングの存在が一致すること、
  および隣接先の重複を数えた場合の反例。
- [等式・帰納法の途中の例](pwl-proof-steps.md) §5 に記す有限ケースで、対合・置換の
  残りの条件、群の積の保存、歩道の始点・終点・辺の保存、および再帰で用いる値の減少。

[design/examples/lean/](examples/README.md) の `lake build` により、次を検査する。

- Ramsey の存在証明と5頂点の反例、Schur の存在証明と4項の反例。
- 任意の有限状態型の DFA に対する、語の分解と任意の k の受理保存。
- 一般の有限二部グラフでの Hall 条件・マッチングの同値性と、専用パターンの列挙の意味。
- 任意の有限部分集合の対合についての偶数性・重みの和、および部分集合の符号反転の例。
- 非可換な群を含む語の簡約、任意の有限置換の互換への分解、任意の辺の関係の歩道から道への変換。
- 一般の鳩の巣原理と、任意の線形順序での Erdős–Szekeres の5項の場合と長い列への拡張。
- 各パターンの証拠を存在命題・選言と証拠の除去へ展開した完全な Lean 版。

Lean 4.31.0 / Mathlib v4.31.0 を固定し、`DecidableEq` と `Fintype` の導出を含めて検査する。
ソースに `sorry`・`admit`・未定義の補助関数は置かない。
Mathlib の一般定理を利用する箇所は [依存関係](examples/README.md) に明示する。

この検査は、数学的な証明と各腕の推論を対象とする。
`.pmop` の構文解析・証明項への変換・Haskell の核による検査、および探索の実行は実装する必要がある。
Lean の存在命題から計算用の値を取り出す条件と、設計上の依存対型の証拠との対応も、核の規則として検査する。
有限列挙の結果を再現できる検証コードとして保存し、提案言語での直接の検証へ接続する作業も含める。
